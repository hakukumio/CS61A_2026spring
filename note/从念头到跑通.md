# 从念头到跑通:一个项目的手工流程

配套实物:`note/demo_loc/`。那是一个真的能跑的小项目,本文每一步都在那里发生过。
边读边跑:`cd note/demo_loc && bash check.sh`

用法:每一步都有 **做什么 / 产出 / 命令 / 合格线**。合格线不过,不许进入下一步。
整个流程 6 步,一个够小的项目 3~5 小时能走完。第一次走会更慢,正常。

---

## 第 0 步 · 立项(15 分钟,一行代码都不写)

**做什么**:写 `README.md`,只回答五个问题,每个问题一句话。

1. 它做什么
2. 输入是什么、从哪来
3. 输出是什么、到哪去
4. 怎么用 —— 写出**真实的命令行**,不是描述
5. 什么算完成 —— 三条,可检查、不需要人来做判断

再加一节 **故意不做什么**,三到五条。

**产出**:`README.md`

**合格线**:五句话能一口气念完,中间不出现"等等""大概""看情况"。
念不顺 = 还没想清楚,继续想,别开始写代码。

**卡住怎么办**:如果写不出第 2、3 条(输入/输出),说明这个想法现在还不是项目,
是一个感觉。换一个能写出具体输入输出的念头。

> demo_loc 的实际结果见 `note/demo_loc/README.md`。

---

## 第 1 步 · 先写"完成的定义"(20 分钟,还是不写主体)

这是全流程里最反直觉、也最值钱的一步。

**做什么**:

1. 在 `data/` 里放 2~3 个真实样例输入
2. **手算**出正确答案,写进 `data/expected.txt`
3. 写 `check.sh`:跑一遍你的程序,把输出和 `expected.txt` 比,一样就 PASS,不一样就打印 diff 并返回非 0

关键一条:`expected.txt` 里的内容必须是**你手敲出来的**,不能是程序打印出来再粘进去的。
后者等于自己给自己判卷。

**产出**:`data/`、`data/expected.txt`、`check.sh`

**命令**:`bash check.sh`

**合格线**:**必须是红的**。而且红得有理有据 —— diff 说"没有 loc.py",而不是"语法错误"。

**为什么必须先写这个**:它是你唯一的"完成"信号。
没有它,你永远处在"差不多好了"的状态,项目会无限膨胀,你也不知道该停在哪。
CS61A 里这个是 `cats.ok` 和 `tests/01.py`。自己做的时候,`check.sh` 就是它。

---

## 第 2 步 · 纵向切一刀(1~2 小时)

**目标**:让 `check.sh` 变绿。就这一个目标。

**做什么**:写最小的一条完整通路 —— 读输入 → 处理 → 输出。
不求对全部情况,不求好看,不求扩展。

**纪律**(违反任何一条都算走偏):

- 允许硬编码
- 只处理样例里的那一种情况
- 不写类、不设计架构、不装任何框架
- 不写 `try`/`except`
- 不写"以后可能会用到"的函数或参数

**产出**:一个丑陋但完整的程序

**合格线**:`bash check.sh` → `PASS`

**立刻做**:`git add -A && git commit -m "walking skeleton"`

> 注意这一步和 CS61A 的顺序是相反的。CS61A 是阶段 1 → 阶段 10,
> 那是横向分层,因为出题人已经替你保证了整体是对的。
> 自己做东西必须纵向切:先打通一条从头到尾的烂路,再往中间塞真东西。
> 没跑通之前写的每一段代码,都是在赌。

---

## 第 3 步 · 找金标准(30 分钟)

**做什么**:给你的输出找一个外部的、不是你写的参照物。

- 有现成工具就对比现成工具(`wc -l`、`git`、系统命令)
- 没有就手算更大的样例
- 拿真实数据跑,别只跑玩具样例

**为什么**:金标准的作用不是判你对错,是**逼你把模糊的词变精确**。

> 真事:这次拿 demo 的 `loc.py` 去数 `proj/cats/cats.py`,
> `loc.py` 说 504 行,`wc -l` 说 503。查下去:那个文件末尾没有换行符。
> 两个都对 —— 只是"行数"的定义不同(`splitlines()` 数的是文本行,`wc -l` 数的是换行符)。
>
> 如果你从没对过答案,你根本不会意识到"行数"是个需要定义的东西,
> 而这个没定义的东西会一直埋在里面,直到某天你拿它做别的事。

**产出**:`README.md` 里多一条"已知的定义取舍",或者代码里多一行注释

**合格线**:你能说清楚"我的输出和参照物在什么情况下会不一样,以及为什么我选我这个"

---

## 第 4 步 · 红绿循环(主体时间,占整个项目 80%)

这一步没有新概念,只有重复。一个循环 = 一次 commit。

1. 跑 `bash check.sh`,看**第一个**红
2. 只改能让它变绿的那一处
3. 再跑 `check.sh`
4. 绿了 → **立刻 commit**;红了 → 回第 1 步

**铁律**:

- 一次只让一个 case 变绿。想同时改三处 = 你不知道是哪处让它绿的
- 绿了不 commit = 白干。下次坏了你回不来
- 同一处改超过 30 分钟没绿 → 停手,用下面的三行法,离开键盘

**怎么知道循环该结束了**:`check.sh` 绿,并且 README 里"什么算完成"那三条都满足。

---

## 第 5 步 · 收紧边界(收尾,30 分钟)

- 回 `README.md`,把"故意不做"按实际情况更新一遍
- 删掉写了但没人调用的代码(会有,很正常)
- 在 README 最后加一节 **我踩过的坑**,写三条

**合格线**:把项目给一个陌生人,他只看 README 就能跑起来。

---

## 卡壳急救 · 三行法

任何时候卡住 —— 不管是报错看不懂、逻辑想不通、还是单纯不知道下一步 ——
停止在脑子里想,打开任意一个文件,写这三行:

```
输入: <具体的一个值>
期望: <具体的输出>
实际: <具体的输出,或完整的报错>
```

大约 80% 的卡壳在这三行写完时就自己解开了,因为"想不通"通常只是"还没写具体"。
剩下 20%,这三行就是你去搜、去问时唯一需要给出去的东西。
给不出这三行,别人也帮不了你 —— 这条对人也一样,包括对我。

---

## 什么时候算完成

不是"功能都做完了"—— 功能永远做不完。是这三条:

1. `check.sh` 绿
2. README 里"什么算完成"那三条满足
3. 陌生人只看 README 就能跑起来

满足就停手,commit,去做下一个。**"再加一个功能"是项目最常见的死法。**

---

## 四种典型走偏

| 症状 | 病因 |
|---|---|
| 写到一半发现不知道要做什么 | 第 0 步跳过了 |
| 上来就设计架构、写类、装框架 | 你还一行能跑的都没有,架构全是猜的 |
| 永远在"差不多好了",没有尽头 | 没有 `check.sh`,第 1 步跳过了 |
| 改了两小时不 commit,某次改动后全崩 | 没有第 4 步的循环 |

## 和 CS61A 的对应关系

你在 cats 里见过这个流程的每一件东西,只是它们都是别人给你的:

| 手册里的步骤 | cats 里的对应物 |
|---|---|
| 第 0 步 立项书 | `lab.md` 的任务描述 |
| 第 1 步 完成的定义 | `cats.ok` + `tests/01.py`~`10.py` |
| 第 2 步 切一刀 | `cats.py` 里的 `# BEGIN PROBLEM 1` |
| 第 3 步 金标准 | 测试文件里的 doctest 期望值 |
| 第 4 步 红绿循环 | 反复跑 `python3 ok` |
| 第 5 步 收拾 | 没有人要求你做 —— 所以这一层你从没练过 |

自己做项目,就是把这张表从右边搬到左边。
